# Maintaining robotframework-browser.org

The site is a static build. There is no CMS, no database and no backend: the
content is Markdown and JSON in `content/`, and every change goes in by pull
request. What is deployed is a directory of HTML files.

If you only want to fix a typo, jump to [Editing content](#editing-content).

## Setup, once

```bash
git clone https://github.com/MarketSquare/robotframework-browser.org
cd robotframework-browser.org
pnpm install
pnpm dev            # http://localhost:3000
```

You need [pnpm](https://pnpm.io/installation) and Node 22. You do **not** need
Python, the Browser library, or a checkout of it — everything the build reads is
committed. (You need [uv](https://docs.astral.sh/uv/) only if you regenerate the
keyword documentation by hand, which the release bot normally does for you.)

## Editing content

### In the browser, with Nuxt Studio

Run `pnpm dev` and click the floating button at the bottom of the page. You get
a visual editor over everything in `content/` — it writes to the files on your
disk, so when you are happy you commit them like any other change.

**There is no hosted Studio, and the deployed site has no editing surface at
all.** The module is loaded by the dev server only. This is deliberate: an
online editor would mean an account system and a backend, and the whole point of
this site is that it has neither.

### In an editor

Content lives in `content/`, one Markdown file per page, and the URL follows the
path: `content/docs/mobile/touch.md` is `/docs/mobile/touch`.

The pages are written in **MDC** — Markdown with components:

```markdown
::::page-section{title="Getting started"}
:::card-grid
::card{title="Install" to="/docs/install"}
Two commands and you are running.
::
:::
::::
```

Nesting is expressed with **more colons on the outer component**, not with
indentation. That trips up everyone once.

**`/styleguide` is the reference.** It renders every component in every state
next to its own source, so it is always accurate. Read it before inventing
markup.

### Version numbers are never typed by hand

Write `%%browser%%`, not `20.3.0`. The tokens are substituted at build time from
`app/generated/versions.json`, and a test fails the build on any token that does
not resolve.

| Token | Is |
|---|---|
| `%%browser%%` | The documented Browser version |
| `%%playwright%%` | The Playwright it is tested against |
| `%%playwrightBundled%%` | The Playwright bundled in the package |
| `%%node%%` | The pinned Node |
| `%%playwrightDockerImage%%` | The base image of the published container |

Release notes are the exception — a note for 20.1.0 says 20.1.0, and the test
skips `content/releases/`.

## Publishing

```
branch → pull request → preview → review → merge to main → live
```

Every pull request builds, runs the tests, and publishes to a
`rfbrowser-pr-<number>.surge.sh` preview that is commented on the PR and torn
down when it closes. Merging to `main` deploys to
[robotframework-browser.org](https://robotframework-browser.org).

Pull requests from **forks get no preview**. `pull_request_target` would fix
that, at the cost of exposing the deploy token to a fork's code; if you want a
preview, push the branch to this repository instead.

Before pushing, this is the same check CI runs:

```bash
pnpm verify         # generate + test + bundle budget
```

## When the library releases

**Do nothing.** `library-release.yml` polls hourly, and within the hour it opens
a pull request that updates the keyword reference, the release notes, the
contributor wall and every version number, with a preview link and a diff of
what changed in the keyword API. Review it and merge.

To pull a release in immediately, or to re-import one: Actions →
**Library release** → *Run workflow*, optionally naming a version.

**Do not hand-edit what it generates.** These files are produced from the
library and your changes will be overwritten:

| Path | Comes from | Regenerated by |
|---|---|---|
| `content/libdoc/Browser-*.json` | Libdoc, run against the released package | `scripts/fetch-libdoc.sh <version>` |
| `content/libdoc/LATEST` | — | the same script, with `--latest` |
| `content/releases/*.md` | `docs/releasenotes/` in the library | `pnpm releases <path-to-library>` |
| `content/contributors.json`, `public/avatars/` | `.all-contributorsrc` in the library | `pnpm contributors <path-to-library>` |
| `app/generated/versions.json` | the library's pins and Dockerfile | `pnpm versions <path-to-library>` |

`pnpm refresh` runs all four against `../robotframework-browser`. It is the only
command that needs the library checked out next door or a network connection —
`pnpm generate` never does, which is why CI can build from a clean clone.

Everything in that table is **committed**. That is the point: the site is built
from what is in this repository and nothing else.

## Two things to know before changing the build

**Keyword pages are not Markdown.** They are rendered from the Libdoc JSON at
build time into one payload per keyword and per type. Grouping comes from each
keyword's defining module via `content/keyword-groups.json`, because Libdoc
carries no group field.

**Server components must stay off the client.** Components under
`app/components/content/` are registered globally for MDC, so a `.server.vue`
file there still ships to the browser. The body belongs in `app/components/`
with a thin wrapper in `content/`, and any `import.meta.glob` must sit *inside*
its `import.meta.server` guard — hoisting one out of the guard once took the
bundle from 391 KB to 1050 KB. `pnpm check:bundle` fails the build if that
happens again.

## Layout

| | |
|---|---|
| `content/` | Every page, as Markdown. Edit this. |
| `app/components/content/` | MDC components — thin wrappers |
| `app/components/` | Their implementations |
| `app/assets/css/tokens.css` | Every colour and size. A test fails on a colour literal anywhere else. |
| `scripts/` | The generators in the table above |
| `.github/workflows/` | Deploy, PR preview, release import |
| `docs/superpowers/` | The design spec and the plans, including why things are as they are |
